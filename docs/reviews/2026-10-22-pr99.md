## Confirmed release blockers

1. **P1: ordinary members can change alert recipients and automation.**
   `staff-routing.functions.ts:141-287` checks workspace membership but never
   requires a company-admin role for any of its four mutations. `save` even reads
   `staff_role` without checking it. The real save/delete/toggle/config handlers
   all accept a synthetic authenticated `staff` context in the independent probe.
   The migration's tenant-only `FOR ALL` policy also permits direct authenticated
   writes, so a server-only role check would leave a second path open. Restrict
   writes in both layers; scope every operation to the authenticated company.
   PostgreSQL confirms a member can add an arbitrary recipient in their own
   company while other-company SELECT remains blocked. This is a role boundary
   finding, not a claim of an observed live cross-company disclosure.

2. **P1: staff alerts bypass the existing send-policy/history pipeline.**
   `wa.server.ts:1042-1077` calls `deliverWhatsAppText(staff.phone, ...)` directly.
   A synthetic real-handler call reaches the provider for a staff recipient with
   no staff conversation, approved template, or stored staff-message evidence.
   The returned delivery outcome is ignored. Use the supported send path with
   explicit admin opt-in, recipient eligibility, applicable template/window
   checks, stable send references, and checked saved/delivery evidence. A message
   assembled from merge tags is not itself an approved provider template. Do not
   forward customer details to newly added numbers by default.

3. **P1: batching can ignore an explicit request for a person.**
   `wa.server.ts:950-956` returns on `skipBotReply` before `needsHumanHandoff`.
   A non-final message saying “human agent” stays stored, but the conversation
   remains bot-enabled/open. Apply the handoff decision to every accepted message
   before deciding which message may trigger an automated response.

4. **P1: a final duplicate suppresses a fresh message.**
   `monitoring.server.ts:588-607` chooses the last sender index before checking
   webhook deduplication. In a batch `[fresh question, already-claimed message]`,
   the first message is saved with `skipBotReply=true`; the second is skipped as
   a duplicate. The independent real-webhook probe observes one fresh inbound
   row and zero AI calls. Select reply work from newly accepted messages, with
   retry/failure behavior that cannot consume and strand earlier work.

5. **P1, source-confirmed: the inter-webhook feature is a cooldown, not a
   trailing debounce.** `wa.server.ts:990-999` returns immediately for a follow-up
   inside the window. No deferred job or pending turn is written. With nothing
   else arriving, the latest question never triggers a later answer. Concurrent
   requests can also both observe the old timestamp. Use durable per-conversation
   work and an atomic revision/claim, and test exactly one eventual response to
   the latest complete burst, including concurrent arrivals and worker retry.
   An edge-worker `setTimeout` alone is not a durable queue.

## Further required corrections

- The migration grants `ALL` to `authenticated`, including `TRUNCATE`. The
  disposable PostgreSQL probe confirms a SQL session in that role can truncate
  both companies' routing rows despite RLS. This does **not** establish a browser
  REST TRUNCATE endpoint. Grant only necessary privileges; avoid browser write
  authority over server-controlled alert recipients.
- Define rollout explicitly. The conversation reads request new columns before
  the SQL exists and ignore read errors; fallback reads omit new assignment
  context. Directory/config read failures look like empty/default-enabled setup.
  Preserve inbound storage and distinguish missing migration/read failure from
  real empty results. Test the chosen before/after-SQL deployment sequence.
- A local `assigned_to` value does not prove an external CRM or WhatsApp app
  agent replied. Do not advertise external coexistence detection without the
  supported provider event path and acceptance evidence. Avoid treating routine
  staff assignment as equivalent to an explicit assistant handoff.
- Validate department output against the enabled directory; do not use arbitrary
  model text as routing authority. Deduplicate canonical recipients and bound
  notifications per lead/turn. Keep actual assignment state and success wording
  tied to checked writes. Pass the real company name to the template renderer.
- Localize the new card in all five supported languages; keep phone numbers
  left-to-right in Arabic. Add accessible names to icon actions and switches.
  `configLoaded` is never reset on a company switch: reset all tenant-bound form
  state and refuse stale saves. Show query errors instead of “no staff”.
- The ten new tests are not listed in `npm test` / `test:whatsapp` at this head.
  CI's green result therefore does not execute them. Add both substantive
  workflow regressions and real-role migration tests to CI.
